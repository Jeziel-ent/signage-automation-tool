# QA and performance audit - 2026-09-28

Scope: backend test suite, frontend test suite, production build, an API smoke test of the whole designer flow, and a
latency/memory profile of the endpoints the pages poll. Everything ran against the **mock engine** on a scratch data
directory; no real CorelDRAW job was run in this audit, and the user's own dev servers and database were not touched.

## Results at a glance

| Check | Result |
|---|---|
| Backend `pytest --maxfail=5 -q` | **757 passed**, 0 failed, 2 warnings (was 755 passed, 222 warnings before the fixes below) |
| Frontend `npm test` (node:test, 17 files) | **201 passed**, 0 failed; every `*.test.mjs` in `src/` is in the npm script |
| Production build (`vite build`) | OK in 6.3 s; one size warning (see "Remaining risks") |
| API smoke test (mock engine) | **17 of 17 steps OK**: brand, upload, add shop, convert, 3 downloads, editor scene, replay, print sheet PDF, ZIP build/download/delete, CorelDRAW health, fonts, path traversal refused (400) |

There is no Vitest or Playwright suite in the repo. Frontend tests use Node's built-in runner, and earlier browser
checks were one-off scripts, not committed tests.

## Bottlenecks found and fixed

Measured in-process (FastAPI TestClient) with 1,001 finished shops in the database, median of 20 calls:

| Endpoint | Before | After | Cause and fix |
|---|---|---|---|
| `GET /api/v2/step-estimates` | 262 ms | **13 ms** | Parsed every shop's full report (each lists every placed object) in Python to read one small field. SQLite now extracts only `timings_s`; malformed reports are skipped. |
| `GET /api/v2/shop-statuses` (50 ids) | 242 ms, 755 KB | **36 ms, 22 KB** | This is what the Automation page polls. Every finished shop's full report was included, which the page never reads. It is now left out of this endpoint. |
| `GET /api/v2/shops/{id}/status` | 3.5 KB | **1.8 KB** | The report was sent twice: the raw database string and the parsed copy. Only the parsed copy is kept. |
| `GET /api/v2/jobs/{id}` | 166 ms, **9.2 MB** | 132 ms, 394 KB | Returned every shop's full report. It is now left out; reports stay available per shop through `/status`. No page currently calls this endpoint. |
| Peak Python memory during the latency loop | 96.8 MB | **16.9 MB** | Follows from the three fixes above. |

Also fixed:
- **220 of the 222 test warnings** came from the `@app.on_event("startup")` handler added in the previous round, which
  FastAPI deprecates. It is now a `lifespan` handler. The startup recovery of shops left stuck by a restart was
  re-checked end to end: a shop left "converting" came back "failed" with the restart message. The 2 warnings left
  come from the test client library.

New tests: `test_status_payloads_stay_light` and `test_step_estimates_average_timings_and_skip_malformed_reports`
(`backend/tests/test_convert_batching.py`). One existing test read the raw `report_json` from `/status` and now reads
`report` (`test_shops_edit.py`).

## Remaining risks (not fixed)

1. **Launch-screen chunk is 1.0 MB (285 KB gzip)**, mostly three.js. It is lazy-loaded, so it doesn't slow the
   main bundle (261 KB), but it is on the first thing everyone sees. The spreadsheet chunk (500 KB) loads only when a
   sheet is imported.
2. **`GET /api/v2/recent` takes 114 ms and returns 288 KB at 1,000 shops**, and it grows linearly: the Recently
   generated page loads every shop ever made. It is refreshed every 3 s only while something is converting. Paging
   becomes worthwhile in the low thousands of shops.
3. **The real CorelDRAW path is not covered by any automated test.** Everything here ran on the mock engine or
   simulated CorelDRAW objects. Conversions, exports and the new 45 s per-shop limit need a live run to confirm.
   The main risk is that 45 s kills slow-but-healthy jobs: CorelDRAW 2019 took 31 s for one shop, one conversion
   took 75 s under memory pressure, and the large Agarpathi masters have never been timed.
4. **Features documented as not verified live**: PDF crop marks and bleed, CMYK JPEG, PNG padding, X7 and native CDR
   saves, text-to-curves, font substitution in exports, and the real wetransfer.com code screen.
5. **Test run time**: the full backend suite takes about 2.5 minutes. 90 s of that is the six WeTransfer tests that
   drive a real Edge window against a local page, and 21 s is the supervisor tests that start real subprocesses.
   Neither is slow in production; both could be marked for opt-in runs if the suite needs to be quicker.

## How to reproduce

```bash
cd backend && ../.venv/Scripts/python.exe -m pytest --maxfail=5 --disable-warnings -q --durations=25
cd frontend && npm test && npx vite build
```

The smoke/latency script was a one-off scratch file: it seeds 1,000 finished shops into a throwaway `SIGNAGE_DATA`
and times each polled endpoint 20 times. It was not added to the repo.
